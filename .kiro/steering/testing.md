# Naqsha — Testing Steering

## Property-based tests

1. Every pure function in `src/codec`, `src/simulator` and `src/exporter` must have property-based tests written with fast-check. Example-based tests are welcome as well, but they never replace the properties.
2. Name each property after the requirement it checks, so a failure points back to the requirement. Use the requirement ID and a plain statement of the requirement once the spec exists. Until then, state the requirement in plain words.
   - Good: `it('R2.1 decoding an encoded card returns the original pattern', ...)`
   - Good: `it('an exported bitmap has one pixel per end and one per pick', ...)`
   - Bad: `it('works', ...)`, `it('property 1', ...)`
3. Write arbitraries that match the card profile in use. Generate the profile or take it as a parameter. Never hard-code dimensions in a test (see `card-geometry.md`).

## Image-processing tests

1. Test `src/reader` image processing against synthetic card images generated by `scripts/make_fixtures.ts`. Do not depend on real photographs.
2. Every generated image uses a fixed random seed, so the same test run always sees the same pixels. Record the seed in the test or in the fixture's ground-truth JSON.
3. Compare the reader's output with the ground-truth pattern written alongside each image.
4. Cover at least the four fixture conditions: clean, noisy, tilted, and noisy and tilted.

## Failures

1. Run properties through `fc.assert`. Do not wrap it in `try/catch`, and do not replace it with a check that hides the failure message.
2. A failing property must be reported with its shrunk counterexample. Copy into your report the counterexample, the seed, and the path that fast-check prints.
3. To replay a failure, pass the reported `seed` and `path` to `fc.assert`. Once the bug is fixed, keep the counterexample as a permanent regression case through the `examples` option.

## Never weaken a property silently

Never weaken a property to make a test pass without telling the user. Weakening includes:

- narrowing an arbitrary so the failing inputs are no longer generated
- adding `fc.pre` or `.filter` to exclude the failing inputs
- lowering `numRuns`
- loosening a tolerance or replacing an equality with a looser check
- skipping, `.todo`, or deleting the property

When a property fails, report the shrunk counterexample and say whether you think the code or the property is wrong. If the property is wrong and needs changing, state exactly what you changed and why before or together with the change, and wait for the user to agree when the change reduces what the property covers.
